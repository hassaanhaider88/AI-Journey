Section 01Foundations

Why Do We Need Pandas?

The problem

You already know how to store data in Python lists. Here's the same three employees, stored the "list" way:

the_list_way.py
names = ["Aman", "Riya", "Rahul"]
ages = [24, 28, 26]
salaries = [40000, 65000, 50000]

Now imagine this at 500 employees, with missing salaries, duplicate entries, and dates mixed in. Ask yourself: can you efficiently analyze this using only lists?

  • Data becomes difficult to organize — three parallel lists, hoping they never drift out of sync.
  • Filtering requires manual loops, every single time.
  • Missing values have no real representation — just gaps you have to track yourself.
  • Grouping "by department" means writing your own bucketing logic from scratch.
  • None of it scales past a toy example.
Data Science Insight

Pandas provides fast, flexible, and easy-to-use data structures for working with structured, real-world data — the same relationship spreadsheets have to a page of handwritten numbers.

From NumPy to Pandas

You already learned the hard part — arrays, vectorization, broadcasting. Pandas is built directly on top of NumPy, and mostly just adds the things a spreadsheet has that an array doesn't.

Section 02Live inspector

Creating & Loading Data

Why do we need this

Before analyzing anything, data has to actually get into Pandas — either you build it yourself, or you load it from somewhere.

Creating a Series

A Series is a single labeled column. It can come from a list, a dictionary, or a NumPy array.

creating_series.py
pd.Series([40000, 65000, 50000])                      # default 0,1,2 index
pd.Series([40000, 65000, 50000], index=["Aman","Riya","Rahul"]) # custom index
pd.Series({"Aman": 40000, "Riya": 65000})                    # dict keys become the index
Output
Aman    40000
Riya    65000
Rahul   50000
dtype: int64

A Series has values (the data) and an index (the labels) — and optionally a name, which becomes the column name once it joins a DataFrame.

Creating a DataFrame
creating_dataframe.py
# dictionary of lists — the most common way
pd.DataFrame({
    "name": ["Aman", "Riya"],
    "salary": [40000, 65000]
})

# list of dictionaries — one dict per row
pd.DataFrame([
    {"name": "Aman", "salary": 40000},
    {"name": "Riya", "salary": 65000}
])

With a dictionary of lists: keys become column names, and each value list becomes a column's values. It's the most common pattern because it mirrors how you already think about data — one list per field.

Loading real data
load_data.py
df = pd.read_csv("employees.csv")     # relative path — looks next to your notebook
df = pd.read_excel("employees.xlsx")
df = pd.read_json("employees.json")

read_csv() is the one you'll use constantly. Its most useful parameters: sep (default is a comma, but some files use ; or tabs), header (which row holds column names), and encoding (only needed when a file has unusual characters and the default UTF-8 fails).

Common Mistake

FileNotFoundError from a relative path that doesn't match where your notebook is actually running. If the file lives elsewhere, either use its full absolute path, or move the file next to your notebook.

Inspecting before analyzing

Never start analyzing right after loading. Read the data first — each function below answers one specific question.

FunctionQuestion it answers
.head()What does my dataset look like?
.tail()What do the last rows look like?
.sample()What does a random slice look like?
.shapeHow many rows and columns do I have?
.dtypesWhat kind of data is stored in each column?
.info()What's the overall structure, and where are values missing?
.describe()What do the basic statistics look like?
Interactive: dataset inspector

This is the real 15-employee dataset from Section 1. Click each function and watch the actual output change.

Try .dtypes — notice salary shows as object, not a number type. That's because some entries are stored as text. Try .describe() next — salary doesn't even appear there, for the same reason. We fix this in Section 4.

Data Science Insight

.describe() only summarizes numeric columns by default. If a column you expect to see is missing from the output, that's usually a dtype problem, not a bug.

Performance Tip

.head() always looks clean because problems often live deeper in the file. .sample() gives you a more honest first impression of messy real-world data.

Section 03Live filtering

Selecting & Filtering Data

Why do we need this

Most of the time you don't need the whole dataset — you need specific columns, specific rows, or only the records matching a condition.

Selecting columns
column_selection.py
df["salary"]                          # one column -> a Series
df[["name", "department", "salary"]]  # multiple columns -> a DataFrame

The double brackets aren't decoration — the outer [] is "select from df," the inner [] is a list of column names. One name → Series. A list of names → DataFrame, even if that list has just one item.

Interactive: loc vs iloc

.loc[] selects by label. .iloc[] selects by position. This table is indexed by employee_id, not 0-5 — switch modes and watch the same input number land on a different row.

Feature.loc[].iloc[]
Selects byLabelsInteger positions
RowsIndex labels0, 1, 2...
Slicing endUsually includedExcluded
Common Mistake

df.loc[0:5] includes row label 5. df.iloc[0:5] stops before position 5. Same-looking slice, different result — this asymmetry trips up almost everyone coming from plain Python slicing.

Interactive: boolean filter

Pick a column, an operator, and a value — the DataFrame filters live.

Combining conditions

    

      
combined_conditions.py

      
df[(df["experience"] > 3) & (df["performance_score"] > 7)]   # AND
df[(df["department"] == "Engineering") | (df["department"] == "HR")] # OR
df[~(df["city"] == "Delhi")]                                          # NOT

    

    
Pandas uses &, |, and ~ — not Python's and/or/not — and every individual condition needs its own parentheses, or operator precedence breaks the whole expression.


    
Useful filtering methods

    

      
filter_methods.py

      
df[df["department"].isin(["Engineering", "Data Science"])]  # match any of several values
df[df["experience"].between(2, 5)]                         # inclusive range
df[df["name"].str.contains("Verma")]                        # text search

    


    

      Real-World Use Case
      
isin() replaces long OR chains when checking against several categories. between() reads cleanly for numeric ranges like salary bands. str.contains() is the go-to for search boxes and free-text filtering.

Cleaning Data


    
Why do we need this

    
Real-world data is rarely clean. This is genuinely one of the largest parts of a Data Analyst's or Data Scientist's actual job — not the modeling, this.


    
Finding missing values

    

      
missing_values.py

      
df.isnull().sum()   # count of missing values, per column

      
Output — computed live from the real dataset

    

    
NaN represents a missing value — isnull() and isna() are the same function under two names, both return True/False, and chaining .sum() counts the Trues per column.

      Common Mistake
      
Dropping every row with any missing value using df.dropna() with no arguments. On a real dataset, one messy column can silently delete rows that were perfectly fine everywhere else. Use subset=[...] to target only the columns that matter.

    


    

      Data Science Insight
      
Median is usually the safer fill for numeric columns like salary — a few extreme outliers can drag the mean far from what's actually typical, while the median barely moves.

    


    
Duplicate values

    
Duplicates happen — the same person entered twice, a failed script re-inserting rows, a copy-paste error. Notice something interesting below: duplicated() checks every column by default, so two rows sharing an ID but differing elsewhere won't be flagged unless you tell it which column to check.

    

      
duplicates.py

      
df.duplicated().sum()                          # exact full-row duplicates
df.duplicated(subset=["employee_id"]).sum()   # duplicates by ID only

drop_duplicates.py

      
df.drop_duplicates(subset=["employee_id"], keep="first")

    


    
Checking & changing data types

    
Section 2 already showed salary quietly reporting as object instead of a number. Here's the actual fix.

    

      
fixing_dtypes.py

      
df["salary"] = pd.to_numeric(df["salary"], errors="coerce")   # bad values become NaN, not a crash
df["joining_date"] = pd.to_datetime(df["joining_date"])           # text -> real dates

    


    

      Common Mistake
      
df["age"].astype(int) crashes the moment it hits a missing value — NaN can't become an integer. pd.to_numeric(..., errors="coerce") converts what it can and turns the rest into NaN instead of stopping your whole script.

    


    
Renaming columns

    

      
renaming.py

      
df.rename(columns={"emp_name": "employee_name"}, inplace=True)

# clean every column name in one line
df.columns = df.columns.str.strip().str.lower().str.replace(" ", "_")

    

    
inplace=True modifies df directly. Without it, rename() returns a new DataFrame and leaves the original untouched.


    
Cleaning inconsistent text

    

      
clean_text.py

      
df["department"] = df["department"].str.strip().str.title()
print(df["department"].unique())

      
Output — computed live from the real messy values

    


    

      Common Mistake
      
Look closely at the output above — .str.title() can mangle acronyms. "HR" becomes "Hr", not "HR". For columns with known acronyms, a manual .replace() or .map() is safer than blindly calling .title().

Modifying Data & Creating New Columns


    
Why do we need this

    
Analysis isn't only reading existing columns — often you're creating new information from what's already there. This is exactly what "feature engineering" means in Machine Learning: existing features, transformed into new ones.


    
Creating & modifying columns directly

    

      
direct_columns.py

      
df["annual_salary"] = df["monthly_salary"] * 12   # new column
df["salary"] = df["salary"] * 1.10              # modify an existing one

    

    
Both are vectorized — same instinct as NumPy. No loop needed for straightforward math.


    
The apply() function

    
apply() runs a custom function against every value in a column — for logic that's too specific for simple arithmetic.

    

      
apply_function.py

      
def performance_category(score):
    if score >= 8:
        return "Excellent"
    elif score >= 6:
        return "Good"
    else:
        return "Needs Improvement"

df["performance_category"] = df["performance_score"].apply(performance_category)

    

    
Value → function → returned category → new column. That's the whole flow, one row at a time under the hood, but written once.


    
Lambda functions

    

      
lambda_functions.py

      
df["salary_level"] = df["salary"].apply(
    lambda salary: "High" if salary > 70000 else "Normal"
)

    

    
A lambda is a small, throwaway function written inline — useful when the logic is a one-liner and doesn't deserve its own named def block.


    
The map() function

    

      
map_function.py

      
department_codes = {"Engineering": "ENG", "Marketing": "MKT", "Finance": "FIN"}
df["department_code"] = df["department"].map(department_codes)

    

    
Use map() for simple value-to-value substitution — a dictionary lookup. Use apply() when the logic needs a real function with branching. That's the whole decision.

      Common Mistake
      
A custom function used with apply() that forgets to return a value — it just computes and stops. The new column doesn't error, it just fills up with None for every row, silently.

    


    

      Performance Tip
      
apply() is flexible but slower than direct vectorized math — same lesson as NumPy. Reach for df["col"] * 2 style operations first, and save apply()/lambda for logic that genuinely needs branching.

Section 06Live ranking

    
Sorting & Ranking


    
Why do we need this

    
After analyzing data, you usually want the extremes — the highest, lowest, best, or worst performing records, not the whole table in whatever order it happened to load in.


    
Sorting values

    

      
sorting.py

      
df.sort_values(by="salary")                        # ascending, default
df.sort_values(by="salary", ascending=False)       # descending
df.sort_values(
    by=["department", "salary"],
    ascending=[True, False]
)  # department A-Z, salary high-to-low within each

    

    
With multiple columns, the first is the primary sort, the second only breaks ties within it — department groups stay alphabetical, and only within each department does salary sort high to low.


    

      Common Mistake
      
sort_values() returns a new DataFrame by default — the original stays untouched unless you pass inplace=True or reassign it: df = df.sort_values(...). Same rule as rename() back in Section 4.

    


    
Ranking

    

      
ranking.py

      
df["salary_rank"] = df["salary"].rank(ascending=False)

    

    
Tied values share a rank by default — two employees tied for 2nd both get rank 2.5, splitting 2 and 3 between them. method="min" gives both rank 2 instead; method="dense" avoids gaps in the rank sequence entirely. Default is fine for most cases.


    
Top & bottom records

    

      
top_bottom.py

      
df.nlargest(5, "salary")              # top 5, no full sort needed
df.nsmallest(5, "performance_score")  # bottom 5

      Performance Tip
      
nlargest()/nsmallest() are faster than sort_values().head() on big datasets — they never sort the rows you don't need.

    


    

      Data Science Insight
      
Before ranking anything, decide upfront whether higher is better. Performance score, higher is better. A "days late" column, lower is better. Getting this backwards silently flips your entire leaderboard.

Grouping & Aggregation


    
Why do we need this

    
"What's the average salary of every department?" You could filter each department manually and average it by hand — five departments, five repeated blocks of code. Or you could ask Pandas once.


    
Split, apply, combine

    
groupby() works in three stages: split the data into groups, apply a calculation to each group separately, then combine the results back into one table.

by group

      →

      →
      
🧩
Combine
into a table

    


    

      
basic_groupby.py

      
df.groupby("department")["salary"].mean()

    


    
Common aggregation functions

    

      
aggregations.py

      
.sum(), .mean(), .median(), .min(), .max(), .count(), .size(), .std()

    

    
count() and size() look interchangeable until missing values show up: size() counts every row in the group, count() only counts the non-null ones. Watch the difference with our real, still-slightly-messy salary column:

    


    
Grouping multiple columns & aggregating multiple columns

    

      
multi_group.py

      
df.groupby(["department", "city"])["salary"].mean()   # hierarchical grouping

df.groupby("department")[["salary", "performance_score"]].mean()  # multiple columns at once

    


    
Multiple aggregations with agg()

    

      
agg_function.py

      
df.groupby("department").agg({
    "salary": ["mean", "max"],
    "performance_score": "mean",
    "employee_id": "count"
})

    

    
One group, several calculations at once, combined into a single summary table.


    
Named aggregation

    

      
named_agg.py

      
department_summary = df.groupby("department").agg(
    average_salary=("salary", "mean"),
    highest_salary=("salary", "max"),
    employee_count=("employee_id", "count")
)

    

    
Clean, readable column names in the output instead of the nested multi-level headers agg() normally produces.


    
Resetting the index

    

      
reset_index.py

      
department_summary.reset_index()

    

    
After grouping, the group column becomes the index, not a regular column. reset_index() turns it back into a normal column — handy the moment you want to sort, filter, or merge on it again.

The Full Workflow, Start to Finish

    
Same dataset, one continuous pipeline — every step is something you already built in this course, just chained together the way a real analysis actually looks.


    

      
full_workflow.py

      
import pandas as pd

# 1. Load
df = pd.read_csv("employees.csv")

# 2. Inspect
df.info()
df.describe()

# 3. Select the columns that matter for this analysis
df = df[["employee_id", "name", "department", "city", "salary",
         "experience", "performance_score", "projects_completed"]]

# 4. Filter out obviously irrelevant rows, if any
df = df[df["employee_id"].notna()]

# 5-6. Find and fill missing values
df["salary"] = pd.to_numeric(df["salary"], errors="coerce")
df["salary"] = df["salary"].fillna(df["salary"].median())
df["age"] = df["age"].fillna(df["age"].median())

# 7. Remove duplicates
df = df.drop_duplicates(subset=["employee_id"], keep="first")

# 8. Correct data types
df["joining_date"] = pd.to_datetime(df["joining_date"])

# 9. Clean up column names and category text
df.columns = df.columns.str.strip().str.lower().str.replace(" ", "_")
df["department"] = df["department"].str.strip().str.title()

# 10. Create new features
df["experience_level"] = df["experience"].apply(
    lambda e: "Senior" if e >= 5 else ("Mid" if e >= 2 else "Junior")
)

# 11. Sort
df = df.sort_values(by="performance_score", ascending=False)

# 12. Group and summarize
department_summary = df.groupby("department").agg(
    average_salary=("salary", "mean"),
    average_performance=("performance_score", "mean"),
    employee_count=("employee_id", "count")
).reset_index()
